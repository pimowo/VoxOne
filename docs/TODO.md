# VoxOne — kanoniczny backlog

> To jest jedyna lista otwartych prac VoxOne. Dokumenty sprzętowe, baseline'y i inventory opisują stan lub historię, ale nie są roadmapą. Po ukończeniu i właściwej weryfikacji zadanie znika z tego pliku; nie prowadzimy sekcji DONE.
>
> Klasyfikacja: `[BUG]` — znany problem, `[STABLE]` — wymagane do wiarygodnego stable, `[DECISION]` — potrzebna jawna decyzja, `[POST-STABLE]` — praca po pierwszym stable, `[HARDWARE]` — projekt lub test sprzętowy.

## Stable hardening

### RADIO

- [STABLE] Wykonać na fizycznym L0 minimum czterogodzinny endurance RADIO: jedna stabilna stacja przez co najmniej 2 h, minimum trzy zmiany stacji i dalsze granie do minimum 4 h.
- [STABLE] Zebrać log z uptime, heap/minimum heap/largest block, PSRAM/minimum PSRAM, stack HWM głównej pętli i DisplayTask, `loopMaxUs`, `audioBuffer`, reconnectami, Wi-Fi oraz RSSI; ocenić trend pamięci, stack, blokady pętli, watchdog/reboot i serie reconnectów.
- [STABLE] Podczas endurance potwierdzić brak trwałych stall/dropout, poprawne ponowne uruchamianie streamu oraz ciągłą reakcję LCD i VU.
- [BUG] Jeśli na realnym streamie nadal wystąpi `Truncated MP3 frame`, przeanalizować ICY stripping, buforowanie, MP3 sync/frame length i Helix przed zmianą dekodowania.

### Bluetooth i VoxOneBT

- [STABLE] Fizycznie przetestować telefon i LG TV: connect, disconnect, reconnect, wielokrotne cykle połączenia, PLAY/PAUSE, volume, metadata, VU oraz wcześniejszy HCI allocation assert.
- [STABLE] Potwierdzić, że A2DP audio state steruje I2S, AVRCP pozostaje transportem/UI, a wybór lub fallback źródła nie wysyła przypadkowego PLAY/PAUSE/NEXT/PREV.
- [STABLE] Sprawdzić BT VU przy PLAY, PAUSE, STOP i disconnect oraz synchronizację VU ON/OFF między klientami WWW i po restarcie.
- [DECISION][SOFTWARE PASS][HIL PENDING] `AVRCP-STOP-LG-EXPERIMENT-1`: osobny wariant VoxOneBT `esp32dev-lg-avrcp-stop` udostępnia wyłącznie testowo prawdziwy `ESP_AVRC_PT_CMD_STOP` (`0x45`) z PRESS/RELEASE, istniejącą polityką TL=0 i diagnostyką odpowiedzi; komenda może być wywołana z USB VoxOneBT bez zmiany MAIN, a zwykły build nadal jej nie udostępnia. Po osobno zatwierdzonym flashowaniu wykonać dokładnie jedną próbę PLAY → STOP → PLAY na LG/YouTube, oddzielając reakcję filmu od A2DP/audio i zachowując możliwość przywrócenia obrazu fizycznego baseline. Na podstawie HIL zdecydować o odrzuceniu eksperymentu albo ewentualnym projekcie funkcji; do tego czasu nie włączać jej do Stable 1.0.0.

### Source Manager i TTS restore

- [STABLE] Wykonać fizyczną macierz RADIO ↔ BT: wybór ręczny, nowy BT connect edge, disconnect, offline, utrata runtime modułu i ponowne połączenie.
- [STABLE] Potwierdzić kontrakt normalnego fallbacku: RADIO PLAY intent wraca do RADIO PLAY, a RADIO STOP intent pozostaje RADIO STOP.
- [STABLE] Potwierdzić wyjątek TTS: utrata BT podczas aktywnego komunikatu nie przerywa TTS, po końcu wybiera RADIO fizycznie STOP i nie uruchamia autoplay; blokada restore jest jednorazowa, a radio intent pozostaje zachowany.
- [STABLE] Potwierdzić manual source priority: istniejące połączenie BT nie cofa ręcznie wybranego RADIO bez nowego connection edge.
- [STABLE] Przy utracie VoxOneBT sprawdzić logical XSMT, MUTE i routing audio; dla przyszłego profilu bez RADIO określić bezpieczny STOP/no-source po utracie wszystkich dostępnych źródeł.

### Kanały L/R i VU

- [STABLE] Odtworzyć kontrolowany materiał: 0–5 s LEFT 1 kHz, 5–7 s cisza, 7–12 s RIGHT 1 kHz, 12–14 s cisza, 14–19 s LEFT+RIGHT; sprawdzić fizyczne kanały i odpowiadające im VU.

### Architecture baseline

Obecny baseline: dane i widoki display są rozdzielone; `HardwareCapabilities` jest autorytatywnym opisem możliwości PCB i zawiera jawny `supportedInputs`; globalny `userVolume` ma zakres 0–100, a czysty Config v7 startuje z bezpieczną wartością 20%; wejście UI emituje znormalizowane zdarzenia, a `UiState` należy do core. `DisplayProfile` jest oddzielony od PCB, a `RuntimeHardwareConfig` od `UserSettings`. M0 ma jeden BIN z backendami SSD1306_128X64 i SSD1309_128X64; wybór przez `RuntimeHardwareConfig` i oba OLED mają wcześniejszy PHYSICAL PASS na tym samym prototypie. Bieżący M0 ma PHYSICAL PASS dla EC11 oraz dla kombinacji display NONE + EC11, SSD1309 + input NONE, NONE + NONE i przywrócenia SSD1309 + EC11; Buttons3 pozostaje BUILD PASS / PHYSICAL NOT TESTED. WIFI-NETIF-HARDENING-1, WIFI-REASSOC-OWNER-1 i WIFI-CONFIG-ATOMIC-REPLACE-1 mają M0 PHYSICAL PASS: HIL A 10/10, poprawny MAIN Web Update app0 → app1 oraz HIL B 5/5; konfiguracja, SPIFFS, hardware i 19 stacji zostały zachowane, a dwie fizyczne wymiany istniejącego `/data/wifi.csv` przeszły poprawnie. Każda bieżąca rodzina dopuszcza runtime `display=NONE` i `input=NONE` jako stan „sprzęt nie jest zainstalowany”, bez zmiany build defaults. Display NONE pomija backend, magistralę, framebuffer i renderer, zachowując DisplayTask dla jego obowiązków pozadisplayowych. `RuntimeHardwareConfig.input` aktywuje przy starcie dokładnie jeden backend EC11, Buttons3 albo NONE; EC11 pozostaje bezpiecznym defaultem bieżących targetów, a oba backendy kończą się na wspólnym `UiInputEvent`. Wspólne linie A/B/KEY obu backendów działają jako `INPUT` i wymagają zewnętrznych pull-upów oraz filtracji sprzętowej. To stan architektury, nie backlog.

Nazwy wariantów display: `STEROWNIK_ROZDZIELCZOŚĆ`, np. `SSD1306_128X32`, `SSD1306_128X64`, `SSD1309_128X64`, `CH1116_128X64`, `SH1106_128X64`, `ST7789V_320X240`, `ST7789_284X76`, `SSD1322_256X64`, `ST7796S_480X320`, `GC9A01_240X240`. Dla modułu opisanego `ST7290_128X64` lub ST7920-compatible trzeba potwierdzić fizyczny kontroler i protokół przed nazwaniem backendu.

RuntimeHardwareConfig, Wi-Fi i początkowy SECURITY OPEN są zapisywane jako jedna odzyskiwalna transakcja; błąd lub przerwanie nie oznacza FIRST BOOT jako ukończonego i pozwala ponowić kreator, a sukces przeładowuje runtime i planuje restart do normalnej pracy. - [STABLE][SOFTWARE FULL IMAGE VALIDATION PASS][RELEASE ARTIFACT/HIL PENDING] Instrukcja [instalacji, aktualizacji i odzyskiwania](FULL_IMAGE.md) opisuje pierwsze programowanie profile-matched `full.bin`, FIRST BOOT, normalne WWW OPEN/PROTECTED, MAIN i SPIFFS, SECURITY Recovery przez KEY, factory reset i powrót do FIRST BOOT, VXCF backup/restore, zachowanie NVS/config oraz różnice W0/M0/L0/S0/DIN0. `VOXONE-STABLE-FULL-IMAGE-VERIFY-1` na czystym `bd5d13f6a4ba7008a8e524bf037aabdd2663ceac` potwierdził offline dla wszystkich pięciu profili poprawną budowę, rozmiar 4 MiB (W0/M0/S0/DIN0) lub 16 MiB (L0), offsety, MD5 tabeli partycji, sumy i integralność bootloadera/app0, początkowe `otadata` wybierające app0, puste NVS i app1, pełny SPIFFS z 8 plikami, tożsamość profilu/build oraz produkcyjny SECURITY. `VOXONE-STABLE-FULL-IMAGE-VALIDATION-FIX-1` usuwa wykrytą lukę walidacji: generator przed scaleniem sprawdza rzeczywiste nagłówki, checksum i validation hash obrazów ESP, MCU i parametry flash, profil i build zapisane w bajtach firmware, powiązanie BIN z ELF przez osadzony SHA-256, wewnętrzny manifest BIN/ELF/build/SECURITY, dokładny layout i MD5 tabeli partycji, kontrakt początkowego `otadata`, pojemność app0 oraz pełny rozmiar, możliwość rozpakowania, dokładny zestaw plików i manifest WWW obrazu SPIFFS.
