# VoxOne — kanoniczny backlog

> To jest jedyna lista otwartych prac VoxOne. Dokumenty sprzętowe, baseline'y i inventory opisują stan lub historię, ale nie są roadmapą. Po ukończeniu i właściwej weryfikacji zadanie znika z tego pliku; nie prowadzimy sekcji DONE.
>
> Klasyfikacja: `[BUG]` — znany problem, `[STABLE]` — wymagane do wiarygodnego stable, `[DECISION]` — potrzebna jawna decyzja, `[POST-STABLE]` — praca po pierwszym stable, `[HARDWARE]` — projekt lub test sprzętowy.
>
> Kanoniczne identyfikatory pięciu bieżących połączeń stanowisk deweloperskich są w [`DEV_USB_PORTS.md`](DEV_USB_PORTS.md). Przyszłe skrypty HIL/OTA mają używać nazw logicznych `L0_NATIVE`, `L0_UART`, `L0_LOG_RX`, `VOXONEBT_USB` i `M0_NATIVE`, nigdy stałych nazw `/dev/tty*`. M0 nie ma obecnie przypisanego zewnętrznego konwertera UART.

## Zamrożony zakres profili 1.0.0

Zatwierdzony kontrakt Technical Stable 1.0.0 obejmuje dwie obowiązkowe
fizyczne bramki profilowe: **S0 i L0**, obie z VoxOneBT. W0, M0 i DIN0
pozostają wspieranymi targetami repozytorium, standardowych buildów,
full-image i testów offline, lecz ich fizyczny HIL nie blokuje pierwszego
Stable. Wszystkie wcześniejsze wyniki tych profili pozostają historycznymi
dowodami w dokładnie zapisanym zakresie.

S0 docelowo używa ESP32-S3 Zero 4 MiB Flash / 2 MiB PSRAM i VoxOneBT.
`RC1-S0-BT-IMPLEMENT-1` ma **SOFTWARE PASS / PHYSICAL HIL PENDING**.
Zatwierdzony pinout rzeczywistego okablowania to UART1 RX44/TX43 i I2S1 RX
BCLK11/WS12/DATA13. OLED używa SDA1/SCL2, I2S0 używa WS4/BCLK5/DOUT6, a
EC11 używa KEY7/B8/A9. Implementacja korzysta ze wspólnego CORE
SourceManager/BtLink/BtAudioInput, a aplikacyjne logi S0 nadal są kierowane
przez natywne USB CDC, ponieważ GPIO43/44 są domyślnymi padami UART0.
Fizyczny HIL S0 dokładnego czystego kandydata nadal
jest wymagany. VU pozostaje na S0 wyłączone,
a aktualizacja VoxOneBT ma używać osobnego USB — MAIN→BT update pozostaje
wyłączone. L0 zachowuje istniejącą PCB V-Tom, hardware, capability i mapę
GPIO. Poza niezbędną obsługą VoxOneBT na S0 oraz poprawkami krytycznymi nowe
funkcje pozostają POST-STABLE.

`RC1-S0-BT-LOCAL-TRANSPORT-1` ma **SOFTWARE PASS / PARTIAL PHYSICAL PASS**;
pełna profilowa bramka S0 pozostaje **PHYSICAL HIL PENDING**.
S0 kompiluje wspólny tryb BT transport dla OLED 128×64 i OLED 128×32. LONG
z BT/PLAYER otwiera stronę `BT TRANSPORT`; wariant 128×64 zachowuje istniejące
sterowanie bez zmian, a kompaktowy wariant 128×32 pokazuje osobno przewijane
wiersze artysty i utworu oraz `< PLAY/PAUSE/STOP >`. Oba renderery używają tej
samej maszyny wejścia CORE bez stanu w warstwie Display: obrót bezpośrednio
wysyła istniejące AVRCP PREVIOUS/NEXT, klik PLAY/PAUSE, LONG wraca do PLAYER,
a timeout pozostaje z Config. Regresyjny stan wyboru OLED32, który przechwytywał
gesty, został usunięty. Widok jest capability-gated; regulacja głośności BT
i RADIO oraz pozostałe gesty zachowują wspólną semantykę. Celowane testy
parytetu OLED32/OLED64, geometrii, wejścia, mapowania transportu, głośności
i ASan/UBSan oraz build S0 z post-link validation mają PASS. Pełny verify na
`02285e26f315eefd8bc30dd17151351296416eb1` ma 161 native, strict transport
16/16, ROM 26/26, ASan/UBSan, pięć standardowych profili i pięć full-image,
regresję full-image validation 10/10, L0 TX-only, WWW repeatability oraz
`git diff --check` PASS. Nie zmieniono UART, VoxOneBT, L0 ani
`VOXONE_VERSION`.

BIN `98aa43f-dirty` o SHA-256
`f0bde6e97629e11035f90cbe7cc4264323fb36bffef1f19e685c00160a0fcf89`
i rozmiarze 1 694 400 B został wgrany i fizycznie zweryfikowany na S0
(BT_TRANSPORT + input + RADIO volume). PASS obejmuje wyłącznie wygląd
BT_TRANSPORT OLED32, dwa przebiegi przewijania, NEXT, PREVIOUS, klik
PLAY/PAUSE, LONG, timeout, głośność PLAYER BT i głośność RADIO. Nie jest to
dowód dla OTA MAIN/SPIFFS, rollback/recovery, Config v7, security ani pełnej
bramki S0. Nadal PENDING pozostają OLED64, disconnect/reconnect, TTS,
nieaktywny BT oraz pełny HIL dokładnego czystego kandydata.

Formalna Definition of Stable liczy teraz **12 głównych bramek**: dwie
profilowe HIL oraz dziesięć niezmienionych grup wspólnych. Statusy oceniono
ponownie względem nowego zakresu, bez automatycznego przenoszenia CLOSED.
`RC1-RADIO-ENDURANCE` zachowuje CLOSED na podstawie terminalnego dowodu
endurance, a profilowe braki RADIO S0/L0 należą do ich bramek profilowych.
`RC1-LR-VU` zachowuje CLOSED na podstawie kontrolowanego fizycznego L0; S0 ma
VU poza zakresem. Bieżący stan to **RC1: 10/12 OPEN, 2/12 CLOSED**.

### Bieżący checkpoint, zatwierdzone zasady i decyzje wymagane przed finalnym RC1

`RC1-S0-BT-IMPLEMENT-1` ma **SOFTWARE PASS / PHYSICAL HIL PENDING**.
Pierwotny zweryfikowany przebieg pochodził z dirty worktree bazującego na
`8ff87067f40610b851fc4491557a4c2c59df2908`; nie jest release identity ani
atestacją bieżącego pinoutu. Checkpoint S0 aktywuje VoxOneBT protocol 2,
BtLink, BtAudioInput i SourceManager, zachowuje I2S0/OLED/EC11 i nie kompiluje
stagingu ani tras MAIN→BT update. Jednorazowa, idempotentna migracja Config v7 używa
odrębnego markera NVS bez zmiany formatu binarnego; po migracji świadome
wyłączenie i VXCF restore pozostają skuteczne. Pełny `tools/verify.ps1` ma
PASS: 160 native, strict transport 16/16, ASan/UBSan, pięć standardowych
buildów, pełne obrazy i negatywna walidacja. S0 `firmware.bin` zajmuje
1685568/1966080 B i ma SHA-256
`c0653f941eb1da4c1bdff6306736a0b7b21f55bec0b9abc88b30c813482bb20d`.
Hash powyżej dokumentuje wyłącznie wcześniejszy dirty build. Przywrócony
pinout UART1 RX44/TX43 i I2S1 RX BCLK11/WS12/DATA13 zachowuje aplikacyjne
logi na native USB CDC i ma SOFTWARE PASS: celowane testy deskryptora S0/L0
oraz kontraktu UART mają 3/3 PASS, a buildy S0 i L0 mają PASS. Artefakt
`98aa43f-dirty` o SHA-256
`f0bde6e97629e11035f90cbe7cc4264323fb36bffef1f19e685c00160a0fcf89`
i rozmiarze 1 694 400 B został wgrany i fizycznie zweryfikowany na S0
(BT_TRANSPORT + input + RADIO volume) wyłącznie w zakresie opisanym powyżej.
Poprzedni artefakt `9fecb710…` jest niepotwierdzony jako wgrany i został
zastąpiony testowo. Rzeczywiste PSRAM, PCM/mono, pełny UART protocol 2,
OTA MAIN/SPIFFS, rollback/recovery, Config v7, security oraz pełny HIL

Poprzedni zachowany czysty checkpoint to

`voxone-rc1-tts-stall-d-closure-1`. Pełny `tools/verify.ps1` ma PASS:

Zatwierdzony zakres HIL: obowiązkowy fizyczny HIL Stable 1.0.0 obejmuje bazową
konfigurację S0+VoxOneBT oraz istniejącego L0+VoxOneBT z macierzy A w

buildów i testów offline, lecz ich fizyczny HIL nie jest release-gating.
Dodatkowe warianty display/audio z bieżących
`HardwareCapabilities` pozostają zaimplementowane, wybieralne i objęte testami
offline/buildami, lecz mają status `OPTIONAL / PHYSICAL HIL NOT QUALIFIED` i
nie blokują Stable. Nie przypisywać im fizycznego PASS bez odpowiednich
dowodów; zachować każdy już istniejący fizyczny PASS we właściwym, historycznie
potwierdzonym zakresie.

Zatwierdzona decyzja L0 XSMT: sprzętowe sterowanie XSMT nie należy do baseline
Stable 1.0.0 i pozostaje POST-STABLE. Bieżąca rewizja L0 nie otrzymuje nowego
GPIO, a `VOXONE_DAC_XSMT_PIN=255` pozostaje bez zmian. Nadal obowiązują
poprawne MUTE, TTS, przełączanie źródeł, cisza przejść i brak niezamierzonego
odtwarzania; przyszłe PCB mogą otrzymać opcjonalne XSMT/MUTE/ENABLE zgodnie z
istniejącym zadaniem POST-STABLE.

Zatwierdzone kryterium `ASYNCTCP-EVENT-ALLOCATION-OOM-1`: do kwalifikacji
akceptować deterministyczną iniekcję OOM wszystkich ścieżek offline pod
ASan/UBSan oraz nieinwazyjny fizyczny HIL L0 potwierdzający lifecycle, READY,
stały bootId, stabilność heap i brak panic/WDT/restartu. Nie wymagać fizycznego
wymuszania OOM ani test-only fault-injection firmware na produkcyjnym L0.
Kryterium zostało w całości spełnione przez wcześniejszy software PASS oraz
ograniczony HIL produkcyjnego L0 `4ef1e53`: historyczna ścieżka `_lagging`
zakończyła się markerem UART i wymuszonym TCP RST, a osobny globalny overload
dostarczył rzeczywistą ramkę close 1013. Oba powiązane P1 są zamknięte;
fizycznej iniekcji OOM nadal nie wykonywać. Nowszy checkpoint programowy
zmienia per-client `_lagging` na ograniczoną próbę wysłania CLOSE 1013 przed
fallbackiem TCP. Odbiór i potwierdzenie tej nowej ramki przez peer pozostają
**PHYSICAL HIL PENDING** i nie przepisują historycznego closeoutu.
Formalny closeout: `reports/VOXONE-RC1-WS-BACKPRESSURE-P1-CLOSEOUT-1.md`.

Zatwierdzona decyzja LG TV PAUSE: rzeczywiste audio A2DP i fizyczna pauza
obrazu, licznika oraz audio mają PASS, lecz MAIN nie zawsze odzwierciedla
PAUSE jako `PAUSED`. Przyczyna pozostaje nieustalona i nie jest przypisywana
LG TV, VoxOneBT ani MAIN. Ograniczenie jest zaakceptowane dla Stable 1.0.0;
nie powtarzać sesji LG TV bez nowej poprawki lub konkretnej hipotezy. Nie
zwalnia to z pozostałych testów BT lifecycle, SourceManager ani TTS.

## Zatwierdzona roadmapa rodzin POST-STABLE

Poniższa roadmapa nie rozszerza release-gating zakresu Stable 1.0.0, który
obejmuje S0 i L0. W0, M0 i DIN0 pozostają zachowanymi profilami buildowymi.
POST-STABLE obejmuje capability ponad zamrożony zakres oraz następne rewizje;
wyjątkiem jest minimalna, jeszcze niewdrożona obsługa VoxOneBT wymagana dla
S0. W0 po wydaniu przechodzi do LEGACY, a Definition of Stable zachowuje
bieżący układ 12 bramek. Docelowe rodziny i ich następne profile są następujące:

| Rodzina | Docelowy MCU | Charakter |
|---|---|---|
| W | klasyczny ESP32 | LEGACY po Stable 1.0.0 |
| S | ESP32-S3 Zero 4 MB flash / 2 MB PSRAM | mini, kompaktowe, także mobilne |
| DIN | ESP32-S3 Zero 4 MB flash / 2 MB PSRAM | funkcjonalnie S, wariant instalacyjny |
| M | ESP32-S3 N16R8 | mniejsze uniwersalne L, także mobilne |
| L | ESP32-S3 N16R8 | stacjonarne domowe; obecne L bez zmian |
| XL | ESP32-S3 N16R8 lub opcjonalnie N32R8 | stacjonarne Full, wyłącznie POST-STABLE |

Historyczny M0 pozostaje profilem ESP32-S3 Zero z niezmienionymi GPIO,
capabilities i wynikami HIL; nie przemianowywać go na S0. Docelowe M z N16R8
otrzyma własny profil M1. Bieżący S0 ma własny pinout fizycznego stanowiska
ESP32-S3 Zero, DIN0 zachowuje tymczasowy pinout M0, a przyszłe S1 i DIN1 mogą
otrzymać nowe mapy GPIO we własnych profilach sprzętowych. Przyszłe L1 i XL1
nie zastępują historycznego L0.

### Docelowa architektura wyświetlaczy

S i DIN obsługują wyłącznie I²C, natomiast M, L i XL obsługują I²C oraz SPI.

całą obsługę L. Na jednej PCB może być aktywny najwyżej jeden wyświetlacz;
`display=NONE` pozostaje dozwolone. Preferowany jest runtime wybór kontrolera,

### Bluetooth, bateria, audio i sieć

VoxOneBT jest obowiązkowym docelowym elementem profilów S0 i L0 w Stable
1.0.0. L0 ma tę capability, a implementacja S0 ma SOFTWARE PASS z
zatwierdzonym pinoutem UART1 RX44/TX43 i I2S1 RX BCLK11/WS12/DATA13;
fizyczny HIL S0 pozostaje PENDING. Dla przyszłych rewizji S/DIN/M/L/XL VoxOneBT
pozostaje capability zależną od konkretnego profilu. W0 nie otrzymuje
rozbudowy, a M0 i DIN0 nie uzyskują BT przez zmianę zakresu HIL. Pomiar
baterii jest planowany dla S i M, przy czym obie rodziny mogą być również
stacjonarne i nie mieć akumulatora. DIN współdzieli funkcjonalność S, lecz
nie wymaga sprzętowego pomiaru baterii.

- [POST-STABLE][HARDWARE] Dla S i M rozstrzygnąć szczegóły pomiaru baterii:
  ADC, kalibrację, prezentację i zasilanie, z zachowaniem wariantów bez
  akumulatora; nie dodawać tego wymagania do DIN ani capability rewizji 0.

Docelowe DSPmini i W5500 są przeznaczone wyłącznie dla XL. Nie dodawać ich do
L0 ani zakresu Stable. Istniejący demonstracyjny transport DSP na L0 pozostaje
historycznym stanem bieżącej implementacji i nie jest deklaracją docelowego
DSPmini. Spotify pozostaje przyszłą opcją POST-STABLE, bez bieżącej
implementacji i bez rozszerzania Stable.

- [POST-STABLE][DECISION][HARDWARE] Rozważyć jedną wspólną PCB dla przyszłych
  L1 i XL1, różniącą się wyposażeniem: L z N16R8 oraz standardowym audio i

### Architecture baseline

Obecny baseline: dane i widoki display są rozdzielone; `HardwareCapabilities` jest autorytatywnym opisem możliwości PCB i zawiera jawne `supportedInputs`, `supportedDisplays` i `supportedAudioOutputs`; globalny `userVolume` ma zakres 0–100, a czysty Config v7 startuje z bezpieczną wartością 20%; wejście UI emituje znormalizowane zdarzenia, a `UiState` należy do core. `DisplayProfile` jest oddzielony od PCB, a `RuntimeHardwareConfig` od `UserSettings`. M0/S0/DIN0 mają wspólne backendy OLED SSD1306 128×32/128×64, SSD1309, SH1106 i CH1116G 128×64 filtrowane przez capability, a L0 przełącza domyślny ST7796 z tymi OLED-ami albo NONE. Wcześniejszy PHYSICAL PASS M0 obejmuje tylko SSD1306/SSD1309 128×64, nie całą obecną macierz. Bieżący M0 ma także PHYSICAL PASS dla EC11 oraz dla kombinacji display NONE + EC11, SSD1309 + input NONE, NONE + NONE i przywrócenia SSD1309 + EC11; Buttons3 pozostaje BUILD PASS / PHYSICAL NOT TESTED. WIFI-NETIF-HARDENING-1, WIFI-REASSOC-OWNER-1 i WIFI-CONFIG-ATOMIC-REPLACE-1 mają M0 PHYSICAL PASS: HIL A 10/10, poprawny MAIN Web Update app0 → app1 oraz HIL B 5/5; konfiguracja, SPIFFS, hardware i 19 stacji zostały zachowane, a dwie fizyczne wymiany istniejącego `/data/wifi.csv` przeszły poprawnie. Każda bieżąca rodzina dopuszcza runtime `display=NONE` i `input=NONE` jako stan „sprzęt nie jest zainstalowany”, bez zmiany build defaults. Display NONE pomija backend, magistralę, framebuffer i renderer, zachowując DisplayTask dla jego obowiązków pozadisplayowych. `RuntimeHardwareConfig.input` aktywuje przy starcie dokładnie jeden backend EC11, Buttons3 albo NONE; EC11 pozostaje bezpiecznym defaultem bieżących targetów, a oba backendy kończą się na wspólnym `UiInputEvent`. Wspólne linie A/B/KEY obu backendów działają jako `INPUT` i wymagają zewnętrznych pull-upów oraz filtracji sprzętowej. To stan architektury, nie backlog.

Nazwy wariantów display: `STEROWNIK_ROZDZIELCZOŚĆ`, np. `SSD1306_128X32`, `SSD1306_128X64`, `SSD1309_128X64`, `CH1116_128X64`, `SH1106_128X64`, `ST7789V_320X240`, `ST7789_284X76`, `SSD1322_256X64`, `ST7796S_480X320`, `GC9A01_240X240`. Dla modułu opisanego `ST7290_128X64` lub ST7920-compatible trzeba potwierdzić fizyczny kontroler i protokół przed nazwaniem backendu.
