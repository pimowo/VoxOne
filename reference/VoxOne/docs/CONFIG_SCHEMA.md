# VoxOne runtime configuration schema

Status: backend schema 8 is stored and validated by ConfigManager. The WWW
panel starts on every MAIN boot; there is no separate CONFIG boot mode.
Most hardware wiring remains planned. Firmware remains 0.4.0.

## Configuration transaction

Editing a WWW field does not change live behavior. Only ZAPISZ:

1. validates the complete configuration and GPIO/resource constraints;
2. writes the complete validated snapshot to NVS;
3. sends the WWW restart response;
4. waits briefly for HTTP delivery;
5. calls ESP.restart();
6. boots with the new configuration.

There is no hot reload. Every persistent save requires a restart. A failed
validation leaves NVS unchanged. Every field below has Restart required = YES.

## Feature flags

| Field | Type | Default | Range/Enum | Visible when | Validation |
|---|---|---:|---|---|---|
| features.web_enabled | bool | false | true/false | hidden/deprecated | retained in NVS only; no runtime effect |
| features.bluetooth_enabled | bool | false for absent key | true/false | always | enables optional external VoxOneBT UART, not local A2DP |
| features.radio_enabled | bool | true | true/false | always | radio fields inactive when false |
| features.play_media_enabled | bool | true | true/false | hidden/deprecated | retained in NVS; no runtime effect |
| features.display_enabled | bool | true | true/false | always | display pins reserved only when true |
| features.encoder_enabled | bool | true | true/false | always | encoder pins reserved only when true |
| features.buttons_enabled | bool | false | true/false | hidden/stored-only | future button mapping |
| features.mqtt_enabled | bool | false | true/false | MQTT section | valid broker settings |
| features.yoradio_ws_enabled | bool | true | true/false | hidden/stored-only | runtime not implemented |
| features.ha_discovery_enabled | bool | false | true/false | hidden/deprecated | retained in NVS only; ignored at runtime |

Holding the encoder at boot does not change mode. WebService and Wi-Fi start
on every boot, irrespective of `features.web_enabled`. With zero enabled
profiles, AP starts immediately. With enabled profiles, STA starts first;
without an address after about 10 s, AP fallback starts. AP remains active
after a later STA connection. The schema-7 `feat_web` key remains in NVS
for compatibility, but is hidden from WWW and ignored at runtime.
MQTT runs when enabled and exposes only the yoRadio-compatible `command`,
`status`, `volume` and `playlist` topics. Native HA Discovery was removed.
The historical `features.ha_discovery_enabled` value remains stored to avoid a
schema migration, stays hidden from WWW and is ignored at runtime. yoRadio WS
remains stored-only today.
`network.ntp_enabled` controls whether TimeService configures NTP.

Disabled modules are not initialized, register no callbacks, do not reconnect,
and reserve no I2S/GPIO/peripheral resources after reboot. Their detailed
settings may remain stored but are inactive.

## PLAY_MEDIA

PLAY_MEDIA is a temporary highest-priority override over RADIO, BT or STOP.
It may play speech generated by HA, MP3, notification sounds, HA media or a supported audio URL,
not a third normal source. HA owns the request queue. It is a system service:
there is no user enable switch and runtime ignores the legacy
`features.play_media_enabled` value.

| Field | Type | Default | Range/Enum | Visible when | Validation |
|---|---|---:|---|---|---|
| play_media.volume_mode | enum | CURRENT | CURRENT/FIXED | hidden/stored-only | future policy |
| play_media.fixed_volume | int | 60 | 0..100 | hidden/stored-only | future policy |

The current runtime always uses shared logical volume 0..100. Changes made
during PLAY_MEDIA remain global after completion. `volume_mode` and
`fixed_volume` remain stored/validated for a future policy and currently have
no runtime effect. Lifecycle: snapshot base source/playback intent ->
suspend/release producer -> acquire PlayMedia -> play -> cleanup -> restore
source. No dedicated speech queue is implemented.

## Bluetooth and radio

The key `feat_bt` and schema version 8 are retained. A previously stored
`feat_bt=true` is not rewritten to false by this migration; the user may
disable it in WWW. The WWW exposes only the external Bluetooth enable switch.
Legacy `bluetooth.*` reconnect settings remain stored
for compatibility, but MAIN does not run a local A2DP reconnect lifecycle.
The external module owns phone pairing. Until MAIN PCM RX is wired, BT
cannot become an audible source even if the UART module reports Ready.
With external BT enabled, fixed DESK UART2 TX17/RX16 are reserved against
active runtime GPIO claims during complete-config validation.

## Wi-Fi profiles (schema 8)

`network.profiles[0..4]` contains SSID (max 32 bytes), password (max 64
bytes), enabled, and priority (0..100; higher wins). Default priorities are
100, 80, 60, 40, 20. An enabled profile needs a nonempty SSID; an empty
password is allowed for an open network. `lastGoodIndex` is -1 or 0..4.
Only five slots exist. Invalid profile input rejects the save before NVS is
written; a corrupted stored profile is isolated by the safe fallback.

NVS uses `w0_ssid`, `w0_pass`, `w0_en`, `w0_prio` through `w4_*` and `w_last`.
All names fit the 15-character Preferences key limit. Legacy `wifi_ssid` and
`wifi_pass` remain as a profile-0 compatibility mirror. On 7 -> 8 migration,
the old SSID/password populate enabled profile 0 at priority 100, the other
slots retain empty/disabled defaults, and `w_last` becomes 0 (or -1 if the
old SSID is empty). The entire snapshot is written and verified before
`cfg_ver=8`; interrupted migration repeats from schema-7 keys. The
`dinaudio` namespace remains untouched.

MAIN starts WebService and Wi-Fi on every boot. The last-good enabled profile
is attempted first, otherwise the highest-priority enabled profile. A failed
profile triggers an asynchronous scan; visible known enabled alternatives are
tried by priority, with last-good and then lower index breaking ties. Scans
have a 30 s cooldown. A successful changed profile updates `w_last` once.
RADIO requires Wi-Fi; NTP does not block audio.

Without any enabled nonempty profile, AP starts immediately at 192.168.4.1.
Otherwise STA starts first. If it lacks an address for about 10 s, AP fallback
starts while STA retries continue. After STA loss the same fallback timer
applies. A subsequent LAN address coexists with AP until reboot. The HTTP
listener is available on both interfaces; no blocking 10 s delay is used.
## GPIO and resource rules

- No active modules may claim the same GPIO.
- Input-only GPIOs are used only for input functions.
- Flash/boot-sensitive pins require explicit safe handling.
- -1 means unused only where the field permits it.
- I2C sharing is allowed only where explicitly supported.
- Display/encoder/BT/Radio/PLAY_MEDIA OFF releases their runtime reservations.
- AudioOutputManager remains the exclusive physical I2S owner.
- Invalid configuration rejects the whole transaction; no partial NVS write.

## StationStore v2 persistence

The radio list is independent from RuntimeConfig schema 8. It is stored in
NVS namespace `stations`, key `list`, as one versioned binary blob
(StationStore data version 1). The header contains magic, version, record
count, next stable ID, payload length and CRC32. Ordered records contain
stable ID, volume trim, UTF-8 name length/name and URL length/URL.

Limits are 16 stations, 48 bytes per name, 192 bytes per direct HTTP/HTTPS URL and
volume trim -20..20. The full worst-case blob is about 3.95 KiB. Missing or
invalid data (including CRC, length, count, duplicate ID or invalid field)
falls back to the three factory stations and writes a verified replacement.
An intentionally empty, valid blob remains empty. Factory reset restores the
three defaults. `radio.default_station` is repaired to the first existing
stable ID, or zero for an empty list.

Full (BT, Radio, PlayMedia, Display, Encoder); Headless (BT, Radio, PlayMedia);
Radio + PlayMedia; BT + PlayMedia; PlayMedia speaker (MAX98357A possible);
Radio only; BT only; and PlayMedia + Display. These are runtime combinations, not
separate firmware variants.

## Startup and schema evolution

Planned startup: load NVS -> validate/recover defaults -> Core/network ->
AudioOutput -> enabled BT/Radio/PlayMedia -> enabled Display/Encoder/Buttons
-> enabled MQTT/yoRadio adapters -> publish state. Final order must respect
the existing App ownership lifecycle.

The repository already has schema history, including schema 3 and migrations.
New fields require an explicit schema increment and migration plan. Migrations
preserve Wi-Fi, password, volume and unrelated existing values.

LEGACY NVS COMPATIBILITY: ConfigManager copies the existing schema 3 keys
from "dinaudio" to "voxone", verifies values and writes the completion marker
last. The legacy namespace stays intact for rollback. Schema 4 -> 5 loads
existing values and schema-5 defaults, validates the complete configuration,
then writes and verifies every field. cfg_ver=5 is written last; an interrupted
write leaves schema 4 for retry on the next boot.
Schema 5 -> 6 loads existing values, supplies ui.navigation_timeout_ms=5000
when absent, validates the full RuntimeConfig, writes and verifies the full
snapshot, and writes cfg_ver=6 last. If interrupted, cfg_ver=5 remains
and migration is retried on the next boot. Schema 6 -> 7 defaults
features.web_enabled to false, then validates and writes a complete snapshot
including NVS key feat_web; cfg_ver=7 is written last. An interrupted migration
leaves cfg_ver=6 and is retried. The legacy namespace is untouched.
